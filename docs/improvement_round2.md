# 第二輪改進：不再堆損失項，改進既有的設計

**原則：不新增任何損失項（loss）**，目前已經有 11 項。這一輪改的是三件事：訓練時怎麼出題、網路看得到哪些資訊、評估時用哪一份權重。每一項都是可以單獨開關的參數，能直接放進消融表。

**判斷「有沒有用」的尺度**，來自「拿掉 Stable Diffusion、批次大小 8」那組實驗（nodds_b8）的兩個隨機種子（seed）。條件是保留測試臉（held-out）、方向一致讀值修正（CR）0.1：

- 同準確率下的 ArcFace：整體差 ≤ 0.003，單一屬性差 ≤ 0.009。
- r18 評審的準確率差 1 到 2 個百分點。

上面這些都算雜訊。新的實驗組（arm）要贏過這個幅度才算數。

## 一、已經寫好的改進

| 編號 | 名稱 | 要不要訓練 | 目前狀態 |
|---|---|---|---|
| 1 | 指數移動平均權重（EMA） | 不用 | 待測 |
| 2 | 訓練時就用 CR（`trcr`） | 要 | **擱置**（見 2b 的抽查結果） |
| 2b | 只在證實讀錯時修正（`vercr`） | 要 | **擱置**（見下方抽查結果） |
| 3 | 速度網路知道自己在第幾層（`layeremb`） | 要 | **不訓練**：量過，問題不存在（見第 3 項的量測結果） |
| 4 | 讀被編輯的那張臉（`recon`） | 要 | **已訓練，通過**（機制 + 不加 CR 的分數，見第 4 項的結果）；評估不加 CR，所以條件 3 不適用 |
| 5 | 只約束負責編輯的那一半速度（`ot_attr`） | 要 | 已寫好；先量現有模型的路徑直度，再決定要不要訓練 |

### 1. 指數移動平均權重（EMA，不用訓練，今天就能測）

- **是什麼**：訓練時一直有另外存一份平均過的權重（`save_models_ema/`，大約是最後 1000 步的平均），但評估一直讀的是最後一步的權重（`save_models/`）。
- **為什麼可能有用**：平均過的權重比較平滑，在生成模型和流模型上常常比最後一步好，而且不用多訓練。
- **改了什麼**：評估時加上 `--ema_weights` 就改讀平均權重，其他都不變。曲線的 `.json` 會記下有沒有用平均權重。
- **算不算亮點**：不算，因為大家都在用。但如果有提升，就是免費的分數，直接併進最終版。

### 2. 訓練時就用 CR（`trcr`）——已擱置

**原本看到的問題（程式碼裡看得到）：**

- 訓練時，每次編輯的方向由**模型自己的條件編碼器（conditioner）** 決定（`train_edit_direction=cond`）。所以流模型從來沒看過「要求的方向」跟「自己的讀值」互相衝突的情況。
- 但評估時，方向是使用者給的。條件編碼器一讀錯，流模型就碰到從沒訓練過的情況，所以才需要推論時用 CR 補救。
- 更糟的是：訓練中，目標損失的方向看的是 **r34 老師**的讀值，流模型的方向看的是**條件編碼器**的讀值。兩者不一致時，流模型被要求往 A 走，損失卻把輸出拉往 B，梯度互相矛盾。訓練紀錄裡的 `dir_disagree_frac` 就是這種情況的比例。

**原本的改法**（`--train_consistent_reading 0.1` 搭配 `--train_edit_direction teacher`）：

1. 方向改由 r34 老師決定，就像評估時由使用者決定。
2. 條件編碼器讀錯邊時，用**跟推論完全一樣的規則**把讀值移到正確那一邊（0.4 或 0.6），再編碼、設目標。
3. 目標損失、CLIP、DDS 都跟著同一個方向，矛盾的梯度消失。

對照組是 `teachdir`：只改方向的來源，不套 CR 規則。

**擱置原因：** 這個做法一律以 r34 為準，等於把模型的判斷整個換掉，所以改成 2b。而 2b 的抽查又顯示，訓練臉上幾乎沒有被證實讀錯的臉，所以兩者都擱置。

### 2b. 只在證實讀錯時才修正（`vercr`）——已擱置

判斷規則寫在 `common/verified_direction.py`，訓練和抽查工具共用同一個函式。

**沒有標準答案，所以無法證明規則永遠正確。能做的只有三件事：讓誤修正很難發生、讓誤修正的傷害很小、把誤修正率實際量出來。**

#### (1) 讓誤修正很難發生：證據要來自會「以不同方式出錯」的來源

| 證據 | 擋掉的錯誤 |
|---|---|
| 兩個架構不同的老師（r34、ConvNeXt） | 單一網路的偏差 |
| 每個老師各看三種版本：原圖、左右翻轉、e4e 重建圖 | 姿勢、反光、構圖造成的誤判；**反演把屬性弄丟**（照片有眼鏡、重建圖沒有，而流模型編輯的是重建圖） |
| 事先算好的 r34 讀值 | 多一票（跟 r34 是同一個網路，不算獨立的證據） |
| 這些讀值至少要跟模型一樣確定（`--verify_beat`） | 模型非常確定、證據卻只是勉強清楚的情況 |

**7 個讀值全部清楚地站在同一邊**、模型在另一邊，才修正。評估用的 R50、r18 **永遠不當證據**。

#### (2) 有矛盾但證據不夠時：不修正，也不教方向（跳過）

| 情況 | 做法 |
|---|---|
| 沒有任何讀值清楚地反對模型 | **照模型**（絕大部分的臉） |
| 全部清楚反對，而且夠確定 | **修正** |
| 有讀值清楚反對模型，但不是全部，或不夠確定 | **跳過**：這張臉這一步不給方向的監督（目標損失、CLIP、DDS 都不算），身分、屬性保持、流模型的似然照常計算 |

實際判斷結果（用訓練程式裡的同一個函式算出來）：

| 模型讀值 | 7 個讀值 | 結果 |
|---|---|---|
| 0.70 | 全部 0.10 到 0.22 | 修正：方向「加」，0.70 → 0.40 |
| 0.20 | 全部 0.10 到 0.22 | 照模型 |
| 0.70 | 原圖都說不是，**重建圖**是 0.55、0.60 | 跳過（可能是反演改變了臉） |
| 0.70 | **翻轉後**變成 0.40、0.45 | 跳過 |
| 0.70 | ConvNeXt 是 0.55 | 跳過 |
| 0.98 | 全部 0.30 到 0.33 | 跳過（模型比證據確定得多） |
| 0.70 | 全部 0.45 到 0.55 | 照模型（沒有人確定，也沒有人清楚反對） |
| 0.30 | 全部 0.80 到 0.92 | 修正：方向「移除」，0.30 → 0.60 |

#### (3) 誤修正的傷害很小

就算 7 個讀值全錯、模型是對的（例如臉其實很年輕，卻全部讀成老），修正後的訓練題目變成「讓這張臉更年輕」。這仍然是合理的要求，也正是推論時使用者可能給的要求。真正的代價只有兩點：

- 編碼時用 0.4 而不是 0.7，等於一點點標籤雜訊。
- 這一步本來要練「變老」，改成練「變年輕」。

#### (4) 抽查結果（2026-11-23）與擱置原因

用 `scripts/audit_verified_direction.py`，以第二階段起點（第一階段 50k 步）的條件編碼器掃描 3000 張訓練臉和 500 張開發臉：

| 屬性 | 修正（訓練臉 / 開發臉） | 跳過（訓練臉 / 開發臉） |
|---|---|---|
| Eyeglasses | 0.0% / 0.0% | 0.5% / 0.4% |
| Male | 0.3% / 0.4% | 10.9% / 10.7% |
| Young | 0.1% / 0.0% | 14.5% / 14.7% |
| Smiling | 0.0% / 0.2% | 12.7% / 14.9% |
| Bangs | 0.2% / 1.0% | 7.1% / 7.9% |

- **幾乎沒有被證實讀錯的臉**：修正只佔 0 到 1%，訓練時沒有東西可以修。
- **跳過大多來自 ConvNeXt 和重建圖**：被跳過的臉裡，r34 看原圖反對模型的只有 3 到 6%，ConvNeXt 反對的卻有 36 到 65%。這是兩個分類器的定義不同，以及反演改變了臉，不是模型讀錯。
- **因此 vercr 和 trcr 都擱置，不訓練。** 這次抽查也找到了更根本的問題，變成第 4 項（`recon`）。

### 3. 速度網路知道自己在第幾層（`layeremb`）

#### 問題（程式碼確認過）

流模型的速度網路對 W+ 的 18 層用**同一組權重**。每一層的「超網路」（產生閘門和偏置的那部分）也只看時間 t 和條件 c，**不知道自己在處理第幾層**。網路唯一能分辨層的線索是那一層本身的數值，但 e4e 的 18 層彼此很接近。

可能的後果：

- 每個屬性的編輯都平均地動到 18 層。
- 方向庫（老師）明明是分層的，例如 `bank_dir_layers 39:0-10` 讓 Young 只動第 0 到 10 層，流模型接手後卻學不到這種分層。
- 動到不該動的層（顏色、細節），可能是 Male 區域保持只有 73 到 75% 的原因之一。

**這只是推論，所以要先量。** `scripts/layer_profile.py`（見第三節第 2 步）會算出每個屬性的編輯在 18 層各佔多少、各層的編輯方向有多相似，並跟方向庫比較。如果現在的編輯已經是分層的，改進空間就小，**不值得訓練**。

#### 量測結果（2026-11-23，nodds_b8 第 100k 步，開發臉 200 張）：問題不存在，不訓練

| 屬性 | 編輯集中在哪幾層（佔編輯量） | 各層方向的平均 cos | flatness |
|---|---|---|---|
| Eyeglasses | 第 2 層 37.7%、第 5 層 17.9%、第 7 層 12.1% | 0.53 | 6.6 |
| Male | 第 5 層 52.6%、第 9 層 13.4% | 0.45 | 9.4 |
| Young | 第 9 層 76.1% | 0.46 | 13.7 |
| Smiling | 第 4 層 58.0% | 0.57 | 10.3 |
| Bangs | 第 4 層 60.8%、第 5 層 10.9% | 0.53 | 10.9 |

- 如果編輯平均地動到 18 層，每層約 5.6%、flatness 接近 0、cos 接近 1。實際上每個屬性都集中在一到三層（flatness 6.6 到 13.7），各層方向也不同（cos 約 0.5），而且每個屬性用的層不一樣。
- 所以速度網路雖然在架構上分不出層，**實際上已經從各層數值的差異學會了分層編輯**。layeremb 要解決的問題不存在，不訓練。程式保留（預設關閉），論文可以用一句話交代「我們檢查過」。
- 表中「bank」那幾列一律是 5.6%，是腳本的錯：方向庫的方向是逐層正規化的單位向量，長度本來就一樣。已改成用方向庫的逐層大小（layer norms）計算，那幾列要重跑才有意義，但不影響上面的結論。
- 另一個觀察（待查）：Young 的編輯有 76% 集中在第 9 層一層。Young 也是同準確率下身分保持最低的屬性，兩者是否有關，還不知道。

#### 設計：把「第幾層」像時間 t 一樣交給超網路

```
原本：h = W x · sigmoid(G [t, c])          + B [t, c]
改成：h = W x · sigmoid(G [t, c] + g_row) + B [t, c] + b_row
```

每一層網路（5 個隱藏層加上輸出層）、每個 W+ 層（18 個）各有一組可學習的 g_row、b_row。數學上等於「把層的獨熱編號接到超網路的輸入」，跟時間 t 的處理方式完全一樣。

#### 每一個可能的質疑，以及怎麼處理

| 質疑 | 處理方式 | 狀態 |
|---|---|---|
| 從舊存檔點接續，起點不同就不公平 | g、b 初始化為 0，接續後的輸出跟原模型**完全相同** | 已驗證：差 0.0 |
| 會不會破壞可逆性和似然 | 仍然是平滑的常微分方程，可逆性和對數行列式都不受影響 | 已驗證：來回編碼誤差 5e-6，跟原本一樣 |
| 新參數學得到嗎 | 每一個新參數都有梯度 | 已驗證 |
| 真的能讓不同層有不同的速度嗎 | 輸入 18 層數值完全相同的資料：原本各層速度差 2e-7（完全一樣），加上之後可以差到 2.9 | 已驗證 |
| 只是參數變多 | 只多 6.1%（221,184 / 3,627,008）。更關鍵的是：如果 18 層共用同一組偏移，就會被原本的偏置吸收，跟原模型是**同一個函數族**。所以原模型本身就是「參數相同、但沒有層資訊」的對照組，多出來的能力只有「知道第幾層」 | 已計算 |
| 以前的層閘門（LayerGate）不就失敗了 | 舊的層閘門是乘在速度上、介於 0 和 1 的閘門，初始值不是 1（接續時會改變模型），訓練後也退化成所有層都打開的常數（見程式碼註解和 `inspect_gate.py` 的紀錄）。新設計沒有「關閉」的目標，不需要正則化，學不到東西就停在 0，也就是退回原模型 | 設計上避開 |
| 層和屬性有沒有交互作用 | 偏移放在 sigmoid **裡面**：某個單元只有在「條件要它開」**而且**「這一層要它開」時才打開，這就是屬性 × 層的交互；輸出層的偏移則直接調整每一層的速度大小 | 設計上就有 |
| 這種影響所有樣本的參數，學習率會不會太大 | Adam 會依每個參數自己調整步長；訓練紀錄會記下 `row_gate_abs`、`row_bias_abs`、`row_spread`（各層偏移的平均大小和差異）。持續暴增才需要調整 | 已加入紀錄 |
| 平均權重、評估、推論編輯器 | 平均權重會跟著更新，接續時新參數從 0 開始；評估和推論編輯器**從存檔點自動偵測**，不會漏掉這些參數 | 已處理 |
| 舊的雙速度場（dof）計算了層閘門卻沒有用到 | 順便修掉：dof 不再計算它，輸出完全一樣，訓練和推論都少一次運算 | 已修正 |
| 第二階段才加入，前 50k 步沒有層資訊 | 第二階段的消融只能當**篩選**；有效的話，要用完整訓練（第一階段就開啟）× 3 個隨機種子，才能寫進論文 | 計畫中 |

#### 刻意不做的事

- **層與層之間交換資訊**（例如在 18 層之間做注意力機制）：目前每一層的速度只看自己那一層。加入交互會改變模型結構，起點無法跟原模型相同，效果也比較難歸因。等這一項有結果再考慮。
- **加任何損失項**：沒有。

#### 怎麼判斷成功

1. **機制有改變**：訓練後再跑一次 `layer_profile.py`，編輯在各層的分布應該變得跟屬性有關（不再平坦），而且更接近方向庫（例如 Young 落在第 0 到 10 層以外的比例下降）。
2. **分數有改變**：跟 nodds_b8 兩個隨機種子比，同準確率下的 ArcFace、屬性保持或區域保持，至少一項的提升大於雜訊（整體 0.003、單一屬性 0.009），而且其他指標沒有變差。
3. **兩個都要成立。** 只有分數變好、機制沒變，就不能說是「因為知道第幾層」。

### 4. 讀被編輯的那張臉（`recon`）——由抽查發現的新貢獻，優先訓練

#### 證據（抽查，2026-11-23）

- 條件編碼器**只看原圖**（`models/conditioner.py`），但流模型編輯的是 e4e 的 W+ 編碼，也就是重建圖；評估時評審看的也是重建圖。
- r34 看原圖和看重建圖時讀在 0.5 不同邊的比例：Male 3.9 到 4.6%、Young 7.1 到 7.7%、Smiling 6.3 到 6.5%、Bangs 3.8 到 4.6%、Eyeglasses 0.2 到 0.5%。
- 在訓練臉上，條件編碼器跟「r34 讀重建圖」不一致的比例，大約是跟「r34 讀原圖」不一致的 2 倍。
- **原版 SDFlow 就有同樣的不一致**：它的屬性估計器介面收 `latent` 參數卻不使用，來源條件讀照片，mi 損失卻讀生成圖（`training/train_sdflow_original.py` 第 84、98 行）。這個問題是從原方法繼承下來的。

#### 理論理由

流模型學的是 p(w | c)，也就是在條件 c 下 W+ 編碼 w 的分布，所以 c 應該描述 w 本身。用原圖讀出 c 時，如果反演改掉了屬性，c 描述的是一張流模型沒有在編輯的臉，等於標籤雜訊；編輯時，流模型也會從錯的起點出發。

#### 改法（`--conditioner_input recon`，實驗組 `recon`）：三個地方一起改，彼此才不會矛盾

| 環節 | 原本 | 改成 |
|---|---|---|
| 條件編碼器讀屬性 | 原圖 | 重建圖 G(latent)（以面積平均縮放到同樣大小） |
| 條件編碼器的知識蒸餾目標 | 事先算好的「r34 讀原圖」 | 即時計算「r34 讀重建圖」：**條件和它的學習目標描述同一張臉** |
| 目標損失的起點 | 老師讀原圖 | 老師讀重建圖（使用既有的 `--target_src_from_recon`） |
| 身分條件 | 原圖 | 不變（只改屬性） |

- 所有呼叫條件編碼器的地方（BN 校正、預覽圖、平均權重、評估腳本）都會自動跟著讀重建圖，不用逐一修改。
- 舊模型預設仍然讀原圖，行為完全不變，之前的結果都不用重跑。
- 評估和推論編輯器會從 `config.json` 自動判斷；推論編輯器要先呼叫 `set_generator(G)`，忘了會直接報錯，不會默默讀錯圖。
- 訓練時重建圖本來就要計算（`losses_vs_recon`），所以只多一次 r34 前向運算，幾乎不增加時間。
- 已用替身生成器驗證：讀原圖、讀重建圖、直接指定輸入、複製平均權重，這四種情況的行為都正確。

#### 怎麼證明它是貢獻（三個都要成立）

### 5. 只約束「負責編輯的那一半速度」的傳輸正則（`ot_attr`）——把 RNODE 改良成自己的方法

#### 觀察

速度是兩個網路相加：`v = v_attr(t, 身分, 屬性, w) + v_base(t, 身分, w)`。`v_base` 計算時屬性被設成 0，所以在「用原本屬性編碼」和「用新屬性解碼」兩邊完全一樣；把 `v_attr` 設成 0，編輯就是原圖不動（已驗證）。**編輯只來自 `v_attr`，`v_base` 負責建模人臉在 W+ 的分布。**

#### 改法（`--transport_target attr`，實驗組 `ot_attr`、`ot_attr_hi`）

| | 照搬 RNODE（`ot`） | 我們的版本（`ot_attr`） |
|---|---|---|
| 懲罰的速度 | 整個 v | 只有 `v_attr`（lag 模式下是 gate × v_attr） |
| `v_base`（建模分布） | 也被限制 | 不受限制 |
| log p 的散度 | 整個速度場 | 整個速度場（不變） |
| 預期效果 | 所有路徑變短變直 | 屬性造成的位移最小、最直（最小作用量的屬性變化） |

這讓 dof 從「架構選擇」變成「機制」：**因為速度被分解，才能只約束負責編輯的那一半。**

#### 已驗證（CPU，小網路）

| 檢查 | 結果 |
|---|---|
| 開或關正則、full 或 attr，軌跡和 log p 是否一樣 | 從相同狀態出發，差異只有 3e-5（z）、4e-4（log p），是自適應求解器多積分兩個量造成的容差差異 |
| `v_attr` 設成 0 | attr 的動能和 Jacobian 都是 0，full 的不是 |
| 梯度 | attr 項的梯度確實傳到負責屬性的網路；傳到 base 網路的只有經由軌跡的間接部分 |
| 解碼也會被計入 | 是 |
| `velocity_field original`（沒有分解）用 attr | 直接報錯 |
| 評估時 | 不受影響（只在訓練開啟） |

**成本：** 開啟傳輸正則時，訓練中每次求解要多積分兩個量，自適應求解器的步數會增加（小網路上 20 → 32），訓練會變慢。原本的 `ot` 也一樣。

#### 量測工具：`scripts/path_straightness.py`

同一批臉、同一個編輯，量：

| 指標 | 意思 |
|---|---|
| `straight_encode`、`straight_decode` | 路徑長度 ÷ 起終點距離（1 = 直線） |
| `attr_share_decode` | 解碼路徑上 ‖v_attr‖ / ‖v‖ 的平均：屬性推動了多少運動 |
| `err_<求解器><步數>` | 用固定 K 步求解時，編輯的相對誤差（越小代表少步數也夠） |
| `nfe_ref` | 參考求解的速度網路呼叫次數 |

已驗證：直線算出 1.00、鋸齒狀算出 1.60；求解結果跟一般求解完全一致；`v_attr` 為 0 時占比為 0。

#### 怎麼證明是貢獻

| 實驗組 | 跟誰比 | 成功條件 |
|---|---|---|
| `ot` | nodds_b8 兩個種子 | 別人的方法的效果（參考） |
| `ot_attr` | nodds_b8 兩個種子，**以及 `ot`** | 同準確率下 ArcFace 不低於基準，而且**優於 `ot`**；路徑更直、少步數誤差更小 |

`ot_attr` 必須贏過 `ot`，才能說「改良」是我們的貢獻；兩者一樣的話，只能說「RNODE 在這裡有效」。投稿前要查文獻，確認「只約束分解速度場的條件部分」沒有人做過。
